# ADR 0001: Guest and Execution Strategy

**Status:** FEASIBILITY IN PROGRESS - shipping backend approval required  
**Date:** 2026-10-14  
**Scope:** Phase 4 feasibility and reference bring-up; not authorization for a shipping backend

## Context

Fang must run a real Android guest and must not misrepresent an external emulator or guest as Fang-owned. The execution API alone is not an Android boot environment: a usable product also needs a guest image, boot/device model, graphics integration, input, storage, audio, lifecycle/error handling, and explicit host/guest security and licensing boundaries.

The inspected host is Windows 11 x64 build 26300, an Intel Core i5-11260H system with 16 GiB RAM, Intel UHD Graphics, and an NVIDIA RTX 3050 Laptop GPU. Vulkan 1.4 enumerates both GPUs (Intel driver 101.7085; NVIDIA driver 610.60). The following local evidence was collected:

- Before the owner-approved probe, Android Emulator 37.2.12 and ADB 37.0.1 were installed but no AVD or bootable system image was installed. The approved API 36 image is now installed; probe results are recorded below.
- `emulator -accel-check` reports `WHPX(10.0.26300) is installed and usable.`
- Windows reports an active hypervisor and Virtual Machine Platform enabled. The optional-feature query reported `HypervisorPlatform` disabled, so this discrepancy should be rechecked before relying on a particular WHPX configuration.
- Android SDK platforms 36, 36.1, and 37.0 are installed; these are development platforms, not bootable guest images.
- Standalone QEMU (`qemu-system-x86_64` / `qemu-img`) is not found on PATH.
- QEMU 11.1.0 was installed from the Software Freedom Conservancy winget package after the owner selected QEMU+WHPX for exploration. Winget metadata identifies QEMU as GPL-2.0.
- Installation command: `winget install --id SoftwareFreedomConservancy.QEMU --exact --source winget --version 11.1.0 --silent --accept-package-agreements --accept-source-agreements`.
- QEMU reports both `tcg` and `whpx` accelerators. A headless, paused, no-disk/no-network QEMU VM opened its monitor and exited cleanly through `quit`. It printed `Ignoring request for interrupt vector 0`; no guest code or Android image was run, so this is only WHPX initialization evidence.
- `qemu-system-x86_64.exe -machine q35 -accel whpx -cpu max -smp 1 -m 512M -nodefaults -no-user-config -display none -serial none -monitor stdio -S` opened the QEMU monitor; `quit` exited it. It printed `Ignoring request for interrupt vector 0`. No guest code or Android image ran, so this is only WHPX initialization evidence.
- QEMU's upstream Windows build instructions require MSYS2/MinGW; this host's PATH compiler is MinGW GCC 6.3 and is not adequate. The winget binary avoids a source build for this initial experiment.
- Android-x86 identifies its latest stable release as Android 9.0-r2 and its `r-x86` development branch as Android 11. Its published source/build workflow is Linux-oriented. The site says Apache-2.0 overall but some components are GPL-2.0-or-later; any selected image must be checked component-by-component.
- QEMU's virtio-gpu documentation describes Android GLES/composer gfxstream capsets as experimental. Its accelerated-graphics requirements do not establish a supported Windows-host Android-gaming graphics path. No guest renderer or frame was observed on this host.
- The installed Android Emulator package contains an Apache-2.0 `LICENSE` file. That does not establish the license of every bundled/transitive component or grant redistribution rights for Android system images. The Android SDK agreement separately covers Android system files and Google APIs add-ons; Google Play images and services require separate review.

## Options

### C. Android Emulator as a non-shipping reference backend

Use a documented AOSP x86_64 system image with the already-installed Android Emulator, WHPX acceleration, and its `gfxstream` graphics backend for a time-boxed guest-boot and compatibility experiment. Keep it explicitly identified as Google's Android Emulator; do not rename or silently bundle it as Fang's engine.

Advantages: lowest-cost way to obtain a real x86_64 Android guest on this host; WHPX acceleration is already reported usable; Android Emulator supplies an existing device model, boot path, ADB integration, and graphics translation for evaluation.

Risks: this is a reference/bring-up path, not evidence of a Fang-owned high-performance runtime; gaming FPS and GPU use are unverified; an AOSP image without Google Play may not support games requiring Google Play services; exact image and component licenses must be reviewed before redistribution.

### A. QEMU system emulation with WHPX and a documented Android guest

Use upstream QEMU with its WHPX accelerator and a compatible Android-x86_64 guest image, then build Fang-owned orchestration and selected device/graphics integrations around that backend.

Advantages: well-documented virtual machine and device model; more replaceable and configurable than treating the full Android Emulator as Fang's backend; QEMU documents `-accel whpx` for Windows, and the installed binary successfully initialized WHPX on this machine.

Risks: no current, suitable Android guest image has been identified. The available Android-x86 releases are old, while building current AOSP requires a Linux build host and substantially more disk/RAM than this machine provides. Android virtio-gpu gfxstream support is experimental and the Windows-host graphics path is unverified. QEMU is GPL-2.0 and requires a deliberate process/distribution boundary and notices. WHPX initialization alone does not show Android can boot, render, or run games.

### B. Android-x86 or another documented Android guest

Use a specific Android-x86 or other documented guest image whose provenance, license, QEMU machine contract, supported devices, and graphics path have been verified.

Advantages: Android-x86 upstream documents x86_64 builds and states its images can run in QEMU/VirtualBox. A prebuilt image might reduce Android boot integration work relative to a custom guest.

Risks: the documented `r-x86` branch is based on Android 11; no exact image has been tested here. Current app compatibility, Google Play services, ARM translation, game DRM/anti-cheat, graphics acceleration, and Windows-host support are unknown. A specific image must receive a component-level license/security review before use or distribution.

### D. Fang-owned VMM directly on Windows Hypervisor Platform

Build a VMM that uses the WHP partition, memory mapping, virtual processor, and exit APIs, plus a separate Android guest and device model.

Advantages: maximum control over Fang-owned orchestration and device interfaces.

Risks: WHP provides virtualization primitives, not Android boot, storage, display, audio, networking, or input devices; device emulation and graphics integration are large and high-risk; no evidence currently shows this path can meet the performance objective on this host.

## Proposed decision

**Recommend Option C only as a temporary, non-shipping development/reference backend.** The owner approved local use of the already-installed Android Emulator and API 36 SDK image for development/reference compatibility work on 2026-10-14. The approval excludes redistribution, Google Play components, and selection as Fang's product backend. This is the only option here with observed API 36 boot, ADB, and a host-GPU reference path. Those observations are not proof of Fang product performance, target-app compatibility, or redistribution rights. Keep the product backend unselected. Do not start direct-WHP implementation or custom QEMU device work without a separate approval.

QEMU remains a research candidate, but another unchanged launch is not justified. First obtain a documented image/machine/device compatibility contract for a chosen guest and agree to the exact next diagnostic. Android-x86 is an alternative source/build candidate, not yet a selected or verified usable image. The owner may instead require an open-source-only path; that choice changes which guest artifacts can be used and will require its own licensing audit.

The already-installed API 36 x86_64 default image and Android Emulator may be used for the approved local-only development/reference work. This does not authorize installing additional images or Google Play services, importing an unapproved APK, sharing host folders, redistribution, or product-backend selection. The host-GPU renderer was verified only in Android Emulator, not upstream QEMU. Before distribution, audit all emulator, image, and transitive licenses.

## Owner-approved feasibility probe (2026-10-14)

The owner selected QEMU+WHPX for a bounded local feasibility test and approved installation of `system-images;android-36;default;x86_64` at revision 2.0.0 (API 36, extension level 17, x86_64, default tag). The image's `package.xml` references the Android SDK license. This is a local test image only; it is not approved for redistribution or as a shipping guest.

The probe used QEMU 11.1.0 with a `q35` machine, WHPX, the image's `kernel-ranchu` and `ramdisk.img`, and read-only system/vendor images under snapshot mode. Networking and host-folder sharing were disabled. QEMU's device list exposed generic virtio and VGA devices but no goldfish/ranchu device models.

- Under WHPX, continuing the paused VM produced `WHPX: Unexpected VP exit code 4`; the VM returned to paused state before any serial output.
- Repeating the same image and device setup with TCG left the VM running but produced no serial output; the VM was then stopped through the QEMU monitor.
- The direct-QEMU serial logs were empty. No Android kernel/boot completion or ADB visibility was observed through upstream QEMU. This is inconclusive boot evidence, not a successful QEMU guest boot and not proof that a fully configured QEMU Android VM cannot boot.
- As a reference comparison, Android Emulator 37.2.12 booted the same API 36 image with WHPX. ADB reported `emulator-5554` online, `sys.boot_completed=1`, and Android release `16`. This confirms that the image itself boots in Google's emulator; it does not validate upstream QEMU integration.
- Android Emulator selected SwiftShader and reported OpenGL ES 3.0 SwiftShader. This is software-renderer identification only; no guest display frame or gaming workload was validated.
- A second reference boot using `-gpu host` selected the NVIDIA RTX 3050 (driver 610.60). Guest SurfaceFlinger reported the NVIDIA OpenGL ES translator and OpenGL ES 3.1. This verifies the Android Emulator host-GPU path only; no frame-rate or game workload was measured.
- A first-party full-screen GLES probe on that reference path sustained 60 Hz for 30 seconds at 64 shader iterations: 1,800 frames, p95 synchronous draw-completion 5.385 ms, p99 6.349 ms, and 0.000% over the 16.67 ms budget. Iteration levels 2, 8, 32, and 64 also stayed within budget in 10-second runs. This is a synthetic `glFinish`-synchronized microbenchmark, not game FPS, not GPU-utilization/thermal evidence, and not QEMU graphics evidence; details and raw local results are in the GLES probe notes.
- The GLES runner now emits an additive schema-v1 provenance sidecar per run. A 5-second validation run recorded a 2.093-second pre-Activity collection interval and 300 draw samples; collection was outside the Activity's measured interval. Effective Windows power mode and independently verified active accelerator remain explicitly unavailable. Existing result JSON/CSV and raw artifacts are preserved.
- The reference launch passed `-net none`, but `netsim` still started and the guest received `10.0.2.x` addresses on `eth0`/`wlan0`; neither interface had a default route. No external traffic was sent, but complete network isolation was not proven. No host-folder sharing was configured.
- The reference AVD was shut down through ADB and its emulator process exited. The ADB server started for the test was also stopped.

The current image is therefore not yet demonstrated to match upstream QEMU's machine/device model. Do not proceed to execution/memory implementation or graphics work on the strength of these probes. The next feasibility step is to establish the Android image's required boot devices and determine whether upstream QEMU can provide them; any custom device-model work or change of guest/backend remains a separate architecture decision.

- **Android API 36 default x86_64 system image, revision 2.0.0:** Its local `package.xml` references `android-sdk-license`. Fang has not implemented or linked a WHP VMM; Windows SDK/platform conditions and any future dependency licenses still require review.
