# Performance Evidence and Phase 9 Gate

This document defines how Fang's host-timing, synthetic GLES, and future real-workload evidence may be used. These tracks measure different systems and must not be combined into one FPS claim.

## A. Phase 1 Host Timing

The Phase 1 benchmark measures Windows host timer scheduling only.

- Clock: `QueryPerformanceCounter` (QPC); its frequency is recorded.
- Scheduling: each trial creates one-shot waitable-timer deadlines at `trial_start + n * interval`. A high-resolution waitable timer is requested; a standard timer is the fallback. The benchmark does not change global timer resolution or thread priority.
- `interval_ns`: QPC elapsed time from the previous observed wake to the current wake; the first interval starts at trial start.
- `wake_lateness_ns`: observed wake time minus its scheduled deadline. Signed early observations are retained.
- Window: only deadlines at or before the configured `duration_ms` end are sampled. Expected samples per trial are `floor(duration_ms * 1000 / interval_us)`.
- Repeatability: `--runs` performs sequential trials; default is 3. There is no warm-up phase. Comparisons should hold host, power mode, background load, duration, interval, and build configuration constant and retain every raw sample.
- Summary: mean, median, and nearest-rank P50/P95/P99 are reported per trial and combined. Even-count median is the arithmetic midpoint.
- JSON: schema version 1 includes run timestamp, configuration, QPC frequency, timer backend, selected host metadata, raw trial samples, and summaries. It omits a Git commit and does not collect GPU utilization or driver version.

Valid use: characterize host timer/wake scheduling and compare host runs under controlled conditions. If a later real workload shows matching host scheduling degradation, this data may inform host diagnostics. It does not establish actual CPU execution latency, guest scheduling cost, a guest bottleneck, GPU throughput, game FPS, or input-to-photon latency.

## B. Android GLES Synthetic Probe

The probe is a first-party Android Activity running a full-screen GLES 3 shader in `GLSurfaceView`. The measured reference path was Android Emulator 37.2.12, API 36 x86_64, WHPX, `-gpu host`, 1080x2400 at 60 Hz, exposing the NVIDIA RTX 3050 and guest GLES 3.1. This is not Fang's product runtime; upstream QEMU has not booted this image.

- Workload: one full-screen triangle; the fragment shader runs a configurable loop of 1-64 iterations. The runner records warm-up and measurement durations and shader iterations.
- Timing boundary: `SystemClock.elapsedRealtimeNanos()` is read immediately before the GL program/uniform/vertex setup and draw submission, then after `glDrawArrays`, attribute cleanup, and `glFinish`. The value includes CPU submission, driver/host synchronization, and completion of the submitted GL work. It is not a GPU-only timer.
- Synchronization: `glFinish` serializes each draw until prior GL work is complete. It changes normal asynchronous rendering behavior and is part of the measured interval.
- Frame count: one sample per completed `GLSurfaceView.Renderer.onDrawFrame` callback inside the measurement window. It is not a count of frames confirmed presented by SurfaceFlinger or displayed by the monitor.
- `over_budget_percent`: fraction of these draw-completion intervals greater than one nominal display refresh period. It is not a verified missed-presentation or dropped-frame metric.
- Output: the runner preserves the existing JSON summary and CSV of raw elapsed/draw-completion samples, and adds a schema-versioned `.manifest.json` sidecar under `out/android-gles-probe/runs/`. Existing runs without a sidecar remain valid; no migration is required. Fields use explicit collected/unavailable states with sources and reasons. Host OS/build/architecture, CPU/RAM, GPU/driver, displays, active power scheme, emulator version, hypervisor capability check, requested emulator modes, guest identity/display/renderer, allowlisted AVD config, installed system-image package/revision, APK hash, Git state, run ID, and workload settings are captured where available. Effective power mode and independently verified active accelerator remain unavailable. Result log correlation uses a unique run ID and does not clear the device-wide logcat buffer. The schema validator checks summary/manifest consistency and CSV/sample counts.
- Timing isolation: host/guest metadata collection completes before Activity launch. Validation runs recorded 2.093 seconds and 1.893 seconds for collection, then exactly 5.0 seconds and 300 GLES samples in the Activity; a final image-identity run also completed the configured 5.0-second interval. This verifies temporal separation for these runs; it does not prove no indirect change to subsequent thermal or background-system state.

Valid use: compare this exact synthetic workload across renderer configurations after preserving the same resolution, refresh rate, emulator/driver, AVD resources, and run settings. It can inform instrumentation design and produce a synthetic renderer baseline. It cannot establish GPU-only execution time, actual presentation cadence, actual game FPS, Fang runtime performance, QEMU performance, thermal stability, or product compatibility. The 60 Hz reference result is not a product target.

| 2. Required virtual devices | Pre-register required display/input, storage, audio, and workload-dependent network devices. Capture guest driver/device evidence and functional I/O tests; a host device list does not pass. | **NOT STARTED** |
| 3. Graphics acceleration | Identify guest renderer/vendor/version and GLES/Vulkan API; render on the guest; exclude software fallback; corroborate host-GPU activity with a named telemetry source. | **BLOCKED** |
| 4. Permitted representative workload | Owner approves workload scope; record app/version/ABI and applicable rights; install and complete a deterministic scenario with required device behavior recorded. | **NOT STARTED** — Free Fire/Free Fire MAX runtime testing is deferred. The first-party animated GLES workload was locally built/launched for graphics-path/instrumentation validation only; it cannot establish game compatibility or gaming FPS. A separate Phase 9 representative workload remains undecided. |
| 5. Frame presentation | Use a verified presentation/fence/frame-timeline source, validate its timestamps and event counts against an independent check, and retain raw data/tool version. `onDrawFrame` and `glFinish` are not presentation evidence. | **BLOCKED** |
| 6. Phase 9 baseline | Gates 1–5 pass; owner approves workload, settings, warm-up, duration, repeat count, formulas, thermal controls, and numeric targets; provenance and raw samples validate; trial variability is reported and baseline is approved. | **BLOCKED** |

See [ADR 0001](decisions/0001-guest-execution-strategy.md) for the option-by-option trade-offs and explicit owner approval list.

**Evidence-gate pass:** the approved guest/workload is reproduced; required configuration fields are complete; multiple trials have retained and count-validated raw samples; each reported metric has a valid source and timing boundary; unavailable metrics are explicitly marked; and trial variability is reported. **Evidence-gate fail/block:** any prerequisite, raw result, setting, or measurement boundary is missing or the workload cannot be reproduced. Passing this evidence gate does not mean product FPS is acceptable; product-performance thresholds remain undecided. Phase 10 is still blocked until actual workload evidence identifies a bottleneck.
