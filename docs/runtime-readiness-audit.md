## Fang Studio local Emulator Player mode

The current launch path is the installed SDK's `emulator\emulator.exe`, not `studio64.exe` and not Android Studio's device manager. The earlier animated-GLES runner starts that executable directly with `-avd <name> -no-snapshot -no-audio -no-boot-anim -gpu host -accel on -port 5554`; its headed mode omits `-no-window`. Fang Studio now discovers the SDK using `ANDROID_SDK_ROOT`, then `ANDROID_HOME`, then `%LOCALAPPDATA%\Android\Sdk`, enumerates AVDs with `emulator.exe -list-avds`, and launches the selected AVD directly with `-avd <name> -gpu host -accel on`. The AVD can be preselected with `FANG_ANDROID_AVD`. AVD-specific launch errors are surfaced; no SDK component or image is installed by this feature.

At this audit, the installed Emulator reports version `37.2.12.0 (build_id 16428233)` and `-list-avds` returns `FANG-StageA-API36-x86_64-headed` and `FANG-StageA-API36-x86_64`. The headed reference AVD config requests x86_64, API 36, 1080x2400 portrait, `hw.gpu.mode=host`, and a 60 Hz virtual display mode. The previous `-accel-check` reported WHPX usable; this is not proof that a particular accelerator or guest graphics path is active. The initial process snapshot contained only the SDK ADB server, with no `studio64.exe`, `emulator.exe`, or QEMU guest process; there was therefore no live pre-existing Android Studio/Emulator process tree to attribute to the earlier window. During the later Fang-started run, the observed process tree included `emulator.exe` with `qemu-system-x86_64.exe` and `conhost.exe` children. The historical run scripts and this test confirm direct `emulator.exe` startup, so an Android Emulator window may be mistaken for the Android Studio IDE; Fang does not start the IDE for this flow.

Fang's Player mode reports **Starting**, **Running**, **Stopping**, and **Failed**, prevents duplicate launches from multiple Fang instances for the same AVD, detects process exit, and provides Start, Stop, Restart, and Open Player controls. Running means the Emulator process and a visible standalone window in its process tree were detected; it does **not** mean Android boot completed. Open Player and Stop locate the window by tracked process IDs, not title. Stop requests a graceful `WM_CLOSE`; Fang does not forcibly terminate a guest when graceful shutdown times out. An AVD lock or an externally started emulator can still reject startup, in which case Fang reports the process exit and directs the user to inspect Emulator startup diagnostics.

This is deliberately an optional **local reference-process adapter**, not a decision to select Android Emulator as Fang's product guest backend. The guest display remains in the Android Emulator's own window; no embedding API or display-surface handoff has been demonstrated. The official [Android Emulator command-line documentation](https://developer.android.com/studio/run/emulator-commandline) identifies `-qt-hide-window` as an Android Studio-integrated-window option and says to omit it for the standalone window; hiding a window is not an embedding interface. The user interacts with that Emulator window directly; Fang does not forward pointer, keyboard, or gamepad input. ADB is a separate documented SDK control channel (the existing runner uses `adb shell input` for test setup), but this UI does not synthesize input or assert guest readiness. The `-gpu host` and `-accel on` command-line options are requests only, not renderer/acceleration verification. Android Studio remains optional for managing or creating AVDs. ADR 0001's local-reference-only and non-redistribution boundaries remain in force.

The backend lifecycle unit tests exercise command argument construction, Starting/Running/Stopping/Failed transitions, launch failures, restart ordering, unexpected exit, and duplicate-start prevention using a fake process driver without starting an emulator. The normal Studio GUI smoke test verifies the Player-mode UI without starting an AVD. A separate authorized local runtime smoke on `FANG-StageA-API36-x86_64-headed` exercised Start, Open Player, Restart, and graceful Stop; the standalone window was detected and focused, and the emulator/QEMU processes exited. ADB listed the emulator device during the run, but this validation did not wait for or claim Android boot completion and did not launch any app. Display embedding/input integration requires a separate supported-API investigation and a demonstrated test before it can be claimed.
